# 版本适配小包说明

（2026-11-11 建。第三批 3G 的交接说明：`hotpot.adapter` 小包里有什么、四个版本（1.20.1 / 1.21.1 / 26.1 / 26.2）的每个意图和每个读写原语该怎么实现、移植时只改哪几个文件。写给以后做版本移植的人看，**改动移植版之前先读这一份**。）

本轮直接复核 1.21.1 原版字节码与 1.20.1 本地兼容实现。26.1 / 26.2 的 API、默认分发和挥手信息来自工作区输入《调研_跨版本写法_右键与存读档.md》，本轮未重新读取其字节码；表中未实测项是移植建议，不代表四版已验收等价。

## 1. 小包的定位

- 包名：`cn.blockforge.generated.orientshotpotchronicles.hotpot.adapter`，放在主工程 `common` 里，**不进前置框架**。
- 只收两类跨版本最容易变的写法：**右键交互的返回值**、**方块实体的存读档**。业务代码只描述「这一下算怎么回事」「要写哪些键」，原版类型和标签读写都关在小包里。
- 只包「意图」和「读写形状」，**不包机制**：什么时候同步、存档结构、键名、槽位语义、组件桥（`pot_contents`）都不在这里。
- 在 1.21.1 上，玩家看到的东西、交互结果、存档格式、ID 一律不变；小包只是把原来散在 15 个右键文件、5 个存读档文件里的原版常量与 `CompoundTag` 读写收拢到一处。

### 2.3 意图为什么是 7 种

调研草稿列了 6 种，实际核过 1.21.1 的原版字节码后拆成 7 种，多出来的是 `CONSUME`：

- `ItemInteractionResult.CONSUME.consumesAction()` 为**真**：`ServerPlayerGameMode.useItemOn` 见到就触发 `ITEM_USED_ON_BLOCK` 并直接返回，既不挥手、也不再让手里的物品处理，**也不为空手重试**。
- `ItemInteractionResult.SKIP_DEFAULT_BLOCK_INTERACTION.consumesAction()` 为**假**：原版只跳过「空手再试」这一步，接着仍会走 `ItemStack.useOn` 让手里物品照常处理。两者落到 `InteractionResult` 也不一样（`CONSUME` / `PASS`）。

两者行为不同，业务上也都用得到（`DrinkCauldronBlock` 锅满时吃掉这一下、`HotPotInteraction` 与 `PlateHolderBlock` 夹着菜时跳过空手），所以必须分开。七种意图与它们的含义：

| 意图 | 含义 | 1.21.1 的用途举例 |
|---|---|---|
| `SUCCESS` | 成功，按「用到了手里的物品」算（客户端挥手、服务端计统计） | 盛汤、下食材、摆餐具 |
| `SUCCESS_SOFT` | 原版 `sidedSuccess`：客户端 SUCCESS、服务端 CONSUME；都算使用物品，不负责替换手持栈 | 叠凳、倒饮料、举杯 |
| `CONSUME` | 吃掉这一下：算用到了物品、不挥手、不走空手、也不再调手里物品 | 饮料锅满了还能倒 |
| `SKIPPED` | 跳过「空手再试」，但仍让手里物品照常处理（`SKIP_DEFAULT_BLOCK_INTERACTION`） | 筷子夹着菜交给筷子、拿方块时不让空手坐下 |
| `PASS_TO_EMPTY` | 放行给「空手再试」 | 拿着东西右键锅 / 灶台开界面 |
| `FAIL` | 失败：不挥手、不改手持物品 | 座位被占、锅位被占 |
| `PASS` | 完全交回原版，什么都不做 | 方块空手侧、物品侧放行 |

## 3. 右键：每个意图在四个版本对应什么

### 3.1 方块「拿着东西右键」（`Use.blockItem`）

| 意图 | 1.20.1 | 1.21.1 | 26.1 | 26.2 | 为什么 |
|---|---|---|---|---|---|
| `SUCCESS` | `compat.ItemInteractionResult.SUCCESS`（`result()` = `InteractionResult.SUCCESS`） | `ItemInteractionResult.SUCCESS` | `InteractionResult.SUCCESS` | 同 26.1 | 四版都表示「算用到了物品」；26.x 的 `SUCCESS` 带 `SwingSource.CLIENT` |
| `SUCCESS_SOFT` | `compat.ItemInteractionResult.sidedSuccess(client)`（客户端 `SUCCESS` / 服务端 `CONSUME`） | `ItemInteractionResult.sidedSuccess(client)` | `SUCCESS`（调研推断，待验） | 现为 `client ? SUCCESS : SUCCESS_SERVER`，不可视为已等价 | 1.21.1 仅客户端挥手；26.x 的建议与现状区别见第 7 节 |
| `CONSUME` | `compat.ItemInteractionResult.CONSUME`（`result()` = `InteractionResult.CONSUME`） | `ItemInteractionResult.CONSUME` | `InteractionResult.CONSUME` | 同 26.1 | 都 `consumesAction` 为真，吃掉这一下 |
| `SKIPPED` | `compat.ItemInteractionResult.SKIP_DEFAULT_BLOCK_INTERACTION`（`result()` = `InteractionResult.PASS`） | `ItemInteractionResult.SKIP_DEFAULT_BLOCK_INTERACTION` | **`InteractionResult.PASS`** | 同 26.1 | 26.x 的 `PASS` 不触发空手逻辑，等价于 1.21.1 的 `SKIP_DEFAULT` |
| `PASS_TO_EMPTY` | `compat.ItemInteractionResult.PASS_TO_DEFAULT_BLOCK_INTERACTION`（`result()` = `InteractionResult.PASS`，再靠 `dispatchUse` 补空手） | `ItemInteractionResult.PASS_TO_DEFAULT_BLOCK_INTERACTION`（默认值） | **`InteractionResult.TRY_WITH_EMPTY_HAND`** | 同 26.1 | 26.x 只有 `TRY_WITH_EMPTY_HAND` 会调 `useWithoutItem`；写成 `PASS` 就会出现「拿着东西右键打不开锅 / 灶台」「筷子夹着菜吃不了」 |
| `FAIL` | `compat.ItemInteractionResult.FAIL` | `ItemInteractionResult.FAIL` | `InteractionResult.FAIL` | 同 26.1 | 一致 |
| `PASS` | 无对应（自造枚举只有 5 个值，别硬塞） | **不提供**，`Use.blockItem` 收到 `PASS` 直接抛 `IllegalArgumentException` | 无对应（26.x 没有 `PASS_TO_DEFAULT` 这种「先交回默认方块交互」的分支） | 同 26.1 | 这一侧表达「交回原版」要用 `PASS_TO_EMPTY`；硬塞 `PASS` 是笔误，让它当场报出来 |

|---|---|---|---|---|

| `SUCCESS_SOFT` | `InteractionResult.sidedSuccess(client)` | `InteractionResult.sidedSuccess(client)` | 参见第 7 节，待按挥手来源验证 | 同样按端分流 |

### 3.3 物品侧（`Use.item` / `Use.itemUse`）

| 意图 | 1.20.1 / 1.21.1 `item` | 26.x `item` | `itemUse`（1.20.1 / 1.21.1） | `itemUse`（26.x） |
|---|---|---|---|---|
| `SUCCESS` | `InteractionResult.SUCCESS` | `InteractionResult.SUCCESS` | `InteractionResultHolder.success(held)` | `InteractionResult.SUCCESS` |
| `SUCCESS_SOFT` | `InteractionResult.sidedSuccess(client)` | `SUCCESS`（调研推断，待验） | `InteractionResultHolder.sidedSuccess(held, client)` | 同左，保留手持变换上下文并验证 |
| `CONSUME` | `InteractionResult.CONSUME` | `InteractionResult.CONSUME` | `InteractionResultHolder.consume(held)` | `InteractionResult.CONSUME` |
| `PASS_TO_EMPTY` / `PASS` / `SKIPPED` | `InteractionResult.PASS` | `InteractionResult.PASS` | `InteractionResultHolder.pass(held)` | `InteractionResult.PASS` |
| `FAIL` | `InteractionResult.FAIL` | `InteractionResult.FAIL` | `InteractionResultHolder.fail(held)` | `InteractionResult.FAIL` |

**要换手持物时**：1.20.1 / 1.21.1 把新栈放进 `InteractionResultHolder` 的第二个参数（`Use.itemUse(outcome, newHeld, client)`）；26.x 没有 `InteractionResultHolder`，用 `InteractionResult.SUCCESS.heldItemTransformedTo(newHeld)`——它返回一个新的 `Success` 记录，把「换了手持物」记在 `ItemContext` 里。**不要**自己造一个 `(result, stack)` 二元组来仿 `Holder`，那会丢掉这个语义。

### 3.4 三处必须知道的原因

1. **1.20.1 没有空手入口。** 它只有一个 `BlockState.use(BlockState, Level, BlockPos, Player, InteractionHand, BlockHitResult)` 返回 `InteractionResult`；原版分发是「`consumesAction()` 就返回，否则交给 `ItemStack.useOn`」，**方块不会再被以空手调一次**。移植版的 `compat.ItemInteractionBlock.dispatchUse` 手工补出这一步：先调内容侧的 `useItemOn`，只有结果是 `PASS_TO_DEFAULT_BLOCK_INTERACTION` 且主手才调 `useWithoutItem`。所以 1.20.1 侧继续用自造的 `compat.ItemInteractionResult` 枚举（5 个值 + `sidedSuccess`），**不要**把 `dispatchUse` 改成返回 `InteractionResult.PASS` 了事——那样空手逻辑会全丢。
2. **三个版本的默认值不同，所以不给默认实现。** 1.20.1 的 `BlockBehaviour.use` 默认 `InteractionResult.PASS`；1.21.1 的 `useItemOn` 默认 `PASS_TO_DEFAULT_BLOCK_INTERACTION`；26.1 / 26.2 的 `useItemOn` 默认 `TRY_WITH_EMPTY_HAND`（1.21.1 本轮核过字节码，其余来自调研记录）。小包的枚举里因此没有「默认意图」，每个入口都显式写；`Use` 也不提供「取默认值」的静态方法。1.21.1 与 26.x 的 `useWithoutItem` 默认都是 `PASS`（1.20.1 没有这个入口，移植版自造的接口默认也是 `PASS`），那一条可以共用。
3. **挥手 / 统计口径三版不同。** 1.20.1 是 `shouldSwing()`（仅 `SUCCESS`）+ `shouldAwardStats()`（`SUCCESS` / `CONSUME`）；1.21.1 是 `shouldSwing()`（`SUCCESS` / `SUCCESS_NO_ITEM_USED`）+ `indicateItemUse()`（`SUCCESS` / `CONSUME`）；26.x 改成 `Success.swingSource()`（`NONE / CLIENT / SERVER`）+ `wasItemInteraction()`。客户端只对 `CLIENT` 挥手、服务端只对 `SERVER` 挥手（输入调研记录称已核对 26.1.2 字节码，本轮未重新核对）。小包**不**「顺手统一」这些口径，只负责把意图换成各版本的原版常量。

## 4. 存读档：每个原语在四个版本怎么实现

### 4.1 方法签名与注册表上下文

| 位置 | 1.20.1 | 1.21.1（主工程） | 26.1 / 26.2 |
|---|---|---|---|
| 写存档 | `saveAdditional(CompoundTag nbt)` | `saveAdditional(CompoundTag nbt, HolderLookup.Provider registries)` | `saveAdditional(ValueOutput out)` |
| 读存档 | **`load(CompoundTag nbt)`**（名字不同） | `loadAdditional(CompoundTag nbt, HolderLookup.Provider registries)` | `loadAdditional(ValueInput in)` |
| 注册表上下文 | 没有 `Provider` 参数 | 每个读写都要带 `Provider` | 上下文在 `ValueInput / ValueOutput` 里（`ValueInput.lookup()` 可取回 `Provider`） |
| 同步包 | `getUpdateTag()` → `saveWithoutMetadata()` | `getUpdateTag(Provider)` → `saveWithoutMetadata(Provider)` | `getUpdateTag(Provider)` **仍返回 `CompoundTag`**：用 `TagValueOutput.createWithContext(ProblemReporter.DISCARDING, registries)` → `saveWithoutMetadata(out)` → `out.buildResult()` 拼出来 |
| 单物品 | `stack.save(new CompoundTag())` / `ItemStack.of(tag)` | `stack.save(registries)` / `ItemStack.parseOptional(registries, tag)` | `out.store(key, ItemStack.CODEC, stack)` / `in.read(key, ItemStack.CODEC).orElse(ItemStack.EMPTY)` |

`TagValueOutput` / `TagValueInput` 是两个版本的桥：`TagValueOutput.createWithContext(ProblemReporter, Provider)`、`TagValueInput.create(ProblemReporter, Provider, CompoundTag)`。26.x 的方块实体存档入口只收 `ValueOutput` / `ValueInput`，**不能直接把 `CompoundTag` 塞进去**，所以 `BeIo` 在 26.x 要提供两个重载：`ValueOutput` 版给 `saveAdditional`，`CompoundTag` 版给同步包与物品组件（移植版 `StorageSupport` 与 `HotPotStorage` 就是这么分的：先 `StorageSupport.output(registries)` 写完再 `nbt.merge(output.buildResult())`）。

### 4.2 写侧原语

| 原语 | 1.20.1 | 1.21.1 | 26.x |
|---|---|---|---|
| `putInt` / `putFloat` / `putDouble` / `putBoolean` / `putString` | `tag.putInt(...)` 等同名方法，键名与标签类型不变 | 同 1.20.1 | `out.putInt(...)` 等同名方法（`ValueOutput` 有全套） |
| `putIntArray` | `tag.putIntArray(key, arr)` | 同 | `out.putIntArray(key, arr)`；注意它和 1.21.1 一样**直接持有数组引用**，业务侧该 `clone()` 的还要 `clone()` |
| `putByteArray` | `tag.putByteArray(key, bytes)` | 同 | **`ValueOutput` 没有 `putByteArray`**，用 `out.store(key, Codec.BYTE_BUFFER, ByteBuffer.wrap(bytes))`；落盘仍是 `ByteArrayTag`（`NbtOps.createByteList` 建的就是它，据输入调研记录，本轮未复核） |
| `putItem` | 空栈跳过；`tag.put(key, stack.save(new CompoundTag()))` | 空栈跳过；`tag.put(key, stack.save(registries))` | 空栈跳过（业务侧判）；`out.store(key, ItemStack.CODEC, stack)` |
| `putItems` | `ContainerHelper.saveAllItems(tag, list)`：键名固定 `Items`、每条带 `Slot` | `ContainerHelper.saveAllItems(tag, list, registries)`，同上 + `Provider` | `ContainerHelper.saveAllItems(out, list)`：内部用 `ItemStackWithSlot.CODEC` 写 `Items`，字段名仍是 `Slot` |
| 空表 | 二参重载的 flag 为 `true` → `Items` 键照写 | 三参重载 flag 为 `true` → 照写 | 默认重载 flag 为 `true` → 不走 `discard`，键照写（据输入调研的字节码记录，本轮未复核） |
| `child` | `new CompoundTag()` + `tag.put(key, child)` | 同 | `out.child(key)` |
| `childList` | `new ListTag()` + `tag.put(key, list)`，每条 `add(new CompoundTag())` | 同 | `out.childrenList(key)` 拿到列表再 `addChild()`；`childrenList` 会**立刻**建好并塞进一个空 `ListTag`，与 1.21.1 写法一致 |

### 4.3 读侧原语

| 原语 | 1.20.1 | 1.21.1 | 26.x |
|---|---|---|---|
| `getInt` / `getFloat` / `getDouble` / `getBoolean` / `getString`（带兜底） | `tag.contains(key) ? tag.getInt(key) : fallback` | 同 | `in.getIntOr(key, fallback)` / `getFloatOr` / `getDoubleOr` / `getBooleanOr` / `getStringOr`；但需区分缺键与错类型：直接 getXxxOr 对错类型通常回 fallback，不能未经差分就替代 1.21.1 的零值 / 空串 |
| `getIntArray` / `getByteArray` | 缺键回空数组 | 同 | `getIntArray(key).orElseGet(() -> new int[0])`；`getByteArray` 对应 `in.read(key, Codec.BYTE_BUFFER)` 再取 `ByteBuffer` |
| `has` | `tag.contains(key)` | 同 | **不能用 `child(key)` 代替任意类型存在性**；用保留原始键的 Tag 桥或独立实现保留类型信息，否则会漏掉数字 / 字符串 / Slot |
| `hasCompound` | `tag.contains(key, Tag.TAG_COMPOUND)` | 同 | `in.child(key).isPresent()`（`child` 只认子标签） |
| `hasNumber` | `tag.contains(key, Tag.TAG_ANY_NUMERIC)` | 同 | 据输入调研 26.x 移除了 `TAG_ANY_NUMERIC`；须保留所有数字类型（含浮点与 byte），用 Tag 桥或完整数字类型判断，不可只试 getInt 或用兜底值代替类型检查 |
| `getItem` | 缺键 / 坏档回 `ItemStack.EMPTY`：`ItemStack.of(tag.getCompound(key))` | `ItemStack.parseOptional(registries, tag.getCompound(key))`，`null` 也回空 | `in.read(key, ItemStack.CODEC).orElse(ItemStack.EMPTY)` |
| `loadItems` | `ContainerHelper.loadAllItems(tag, list)` | 带 `Provider` | `ContainerHelper.loadAllItems(in, list)` |
| `items()`（旧档兜底） | `tag.getList("Items", Tag.TAG_COMPOUND)`，逐条 `contains("Slot")` | 同 | `childrenListOrEmpty("Items")` + `MAP_CODEC` 可参考现有移植实现；须另验 Slot 的任意类型存在性、getByte 截断及无符号 `& 255`，与无 Slot 的顺序兜底严格区分 |
| `child` / `children` | 缺键回空 reader / 空列表 | 同 | `childOrEmpty(key)` / `childrenListOrEmpty(key)`（`childrenList(key)` 返回 `Optional`） |

### 4.4 哪些键照样要由业务写

小包只改「怎么写」，不改「写什么」。主工程要求保留的键名、结构、槽位语义如下（`Base*` / `Spicy*` / `Doneness` / `Cooked` / `Overcook` / `SlotXp` / `PendingXp` / `Items`（每条带 `Slot`）/ `Plates` / `Fuel` / `Portions` / `Kinds` / `Item` / `Cuts` / `Pounds` / `ItemFacing`），所以业务里的键名一个都不能改；现有移植版落后的字段不代表应删，见第 7 节。缺键、坏档的兜底值也和改造前一致：数值仅缺键时回 `fallback`；有键但错类型时保留原版零值 / 空串；数组回空数组、物品回 `ItemStack.EMPTY`、子节点回空 reader、子节点列表回空列表。

已经走 `BeIo` 的五个业务文件：`HotPotStorage`（锅，`HotPotBlockEntity` 保留原有转调）、`StoveBlockEntity`、`SauceStationBlockEntity`、`PlateHolderBlockEntity`、`CuttingBoardBlockEntity`。桌面用 `childList("Plates")` / `addChild()` 保存餐具，再由子节点保存物品、朝向与位置；同步包仍走 `SyncedBlockEntity.getUpdateTag` → `saveWithoutMetadata`。

## 5. 移植时只改哪几个文件

**必改 4 个**（都在 `adapter` 包里）：

| 文件 | 改什么 |
|---|---|
| `Use.java` | 四个入口的方法体与返回类型：1.20.1 返回自造的 `compat.ItemInteractionResult` / `InteractionResult` / `InteractionResultHolder`；26.x 全部返回 `InteractionResult`（`itemUse` 换手持物用 `heldItemTransformedTo`） |
| `CompoundWriter.java` | 1.20.1 去掉 `Provider`；26.x 换成写 `ValueOutput`，字节数组走 `Codec.BYTE_BUFFER`、单物品走 `ItemStack.CODEC`、物品列表走 `ContainerHelper.saveAllItems(out, list)` |
| `CompoundReader.java` | 同上。26.x 的标量可用 `getXxxOr`，但要额外保留「键存在且类型错误→原版零值」语义；任意键存在性 / 数字类型 / Slot 字节须借 Tag 桥验证，不能简单用 child 判断；数组、列表及 MAP_CODEC 逐字验收 |

**不用改**：`UseOutcome`、`StoreWriter`、`StoreChildList`、`StoreReader`、`StoredItem`（接口与枚举四版一致）。

**业务文件**：15 个右键文件的返回表达式可复用，但方法头、原版类型 import、1.20.1 的分发接线仍须按版本改；存读档的 5 个文件只改方法头（1.20.1 是 `load`，26.x 是 `ValueInput`，`Provider` 参数的有无），方法体里的 `w.xxx` / `r.xxx` 一行不动——这正是小包要省的那部分。

**不归小包的差异**（改法见别处，不要硬塞进来）：`onRemove` → `affectNeighborsAfterRemoval` / `preRemoveSideEffects`（方块被破坏掉什么）；物品组件 ↔ NBT（`pot_contents`、`collectImplicitComponents` / `applyImplicitComponents` / `removeComponentsFromTag`）；`SUCCESS_SERVER` 的观感判断；注册 ID、渲染、界面、配方。

## 6. 怎么核对没改坏

- `Opt3gAdapterTest` 把「意图 → 1.21.1 原版常量」的映射钉死（含 `CONSUME` 与 `SKIP_DEFAULT` 语义不同这一条），并做读写原语的往返、`putItems` 与 `ContainerHelper.saveAllItems` 逐字相同、空表仍写 `Items` 键、子节点类型等断言。改小包后先跑它。
- 移植版改动前后对照：把每个 `return` 的原版常量列成表逐条比（业务侧改前是什么、换成意图再换回来是什么），全部相同才算过。
- 存档：改前改后各开一次开发服，放好五种方块实体（锅、灶台、蘸料台、桌面、砧板），改内容、保存退出、重开，读出的 NBT 与同步包逐字比。
