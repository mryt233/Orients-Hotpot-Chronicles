# 前置内嵌与多版本兼容方案

（作者：mryt233，2026-11-01。记录用户提出的问题：火锅、面条等系列都可能内嵌 `orient_framework` 前置；旧系列内置旧前置、新系列内置新前置时，怎么能共存，而不是直接拒绝或冲突。2026-11-01 经只读复核修正了 Fabric / NeoForge 的版本选择结论。）

## 1. 问题

公开版为了“玩家只装一个 jar”，会把 `orient_framework` 作为嵌套 jar 放进内容 jar：

- Fabric：`META-INF/jars/` + `fabric.mod.json` 的 `jars`
- NeoForge：`META-INF/jarjar/` + `metadata.json`

如果玩家同时装火锅新版（内嵌 Runtime 新版）和面条旧版（内嵌 Runtime 旧版），两个内容 jar 都带着同一个 mod ID 的 Runtime，需要知道加载器会怎么处理。

## 2. 两个加载器的实际行为（已核对源码）

### Fabric Loader 0.19.3

Fabric 有依赖求解器（`ModSolver`），不是“看到同 ID 两个版本就直接报 duplicate”：

- 同一个 mod ID 的多个候选可以同时存在于安装包中，求解器会按硬依赖选出一个满足条件的版本；最终只加载一个。
- `ModDiscoverer` 的 `jijDedupMap` 按嵌套 jar 哈希去重只是发现阶段的优化，不是唯一的兼容机制；**不同字节/不同版本仍然可以是两个候选**。
- 外置 root 候选在排序上优先，但不是无条件覆盖；硬约束可能让内嵌候选胜出。
- `jars` 只声明发现路径，`depends` 声明必需范围，`breaks` 排除已知坏版本；它们不提供独立类加载空间。
- Fabric 版本范围字符串里，空格表示 **AND**，数组元素表示 **OR**；上下界不要拆成数组。
- 约束有解时加载成功；无解时报 `ModResolutionException` / “不兼容 mod 集合”。`duplicate mod` 是最终选中集合重复 ID 的保护错误，不是发现多个嵌套候选就必然触发。

### NeoForge 21.1.265 / FML 4.0.45 / JarJarSelector 0.4.1

- JarJar 按 **group + artifact** 聚合，不按 mod ID 聚合；各系列必须使用同一坐标（当前正式脚本已经统一）。
- 必须同时满足：版本范围有交集，**并且实际有内嵌候选落在交集里**；它不会联网补齐版本。
- 当前 `JarSelector` 对满足交集的候选用 `findFirst()`，**没有最高版本排序**；不能把功能正确性建立在“肯定选新 Runtime”上。
- 普通/根 mod 的同 ID 重复由 `UniqueModListBuilder` 处理，可能按版本挑最新；旧内容如果精确锁旧版，遇到新 Runtime 被选中仍会失败。

## 3. 版本字符串是当前最大的隐患

Fabric 和 NeoForge（Maven 比较）对同一字符串的排序不同：

| 比较 | Fabric | NeoForge / Maven |
| --- | --- | --- |
| `0.1.0-hotfix1` 对 `0.1.0` | 小于 | 大于 |
| `0.1.0-hotfix10` 对 `0.1.0-hotfix2` | 小于 | 大于 |
| `0.2.0-pre` 对 `0.2.0` | 小于 | 大于 |

后果：

- Fabric 的 `>=0.1.0-hotfix1` **仍然接受 `0.1.0`**，因为 Fabric 把 `0.1.0` 排在 hotfix1 后面。
- `<0.2.0` 会接受 `0.2.0-pre`。
- **已采用（用户 2026-11-01）**：Runtime 用递增数字版本，当前 `0.1.1`，不再使用 `0.1.0-hotfixN` 这类双端排序不一致的写法。
- Fabric 若要排除下一系列预发布，可使用 `<0.2.0-`。
- 所有范围边界要在 Fabric 和 NeoForge 上分别实测，不能只测一边。

## 4. 推荐的兼容契约

### 4.1 内容包声明 API 兼容范围

不要再用精确锁：

```text
（旧写法，已废弃）
Fabric:   =0.1.0-hotfix1
NeoForge: [0.1.0-hotfix1]
```

改成兼容范围（示例；最终以实际 API 版本为准）：

```text
Fabric:   >=0.1.1 <0.2.0
NeoForge: [0.1.1,0.2.0)
```

（2026-11-01 已按此实施：内容包 hotfix4 与单 jar 都改成这个范围。）

- `0.1.x` 内只加 API、不删/不改已有行为；补丁和 hotfix 都向后兼容。
- 破坏性变更进 `0.2.0`，内容包再升到新范围。
- 内容包的 NeoForge `versionRange` 与 JarJar `range` 必须反映一致的必需下限；否则 JarJar 可能选出旧版，随后内容依赖检查才失败。

### 4.2 API / ABI 兼容

- **运行版本查询不能是 `public static final String`**：内容包编译时可能把值内联，读到自己的编译值。应通过稳定方法查询，并且这个方法必须存在于最低支持的 Runtime 中。
- 不仅不能删方法，也不能随意改构造器、返回类型、接口要求。
- `ModuleDeclaration` 是公开 record，新增字段会改变规范构造器签名；旧内容编译产物可能直接 `new ModuleDeclaration(...)`。
- 给旧内容实现的接口新增抽象方法，可能触发 `AbstractMethodError`；必须给 default 实现或升主版本。
- 用**未重新编译的旧内容 jar**验证新 Runtime 的 ABI，不能只测重新编译的源码。

### 4.3 可选能力隔离

`if (hasFeature(...))` 不能保护入口类、父类、字段类型、Mixin 或静态初始化器里的新 API 引用。做法：

- 把可选实现放进独立适配类；确认能力后再加载/调用。
- 反射只用于确有必要的兼容边界，不滥用。
- 本地 `hasFeature` 不代表远端支持；网络功能必须双方协商能力。
- 协议、存档组件、注册 ID、配置和资源格式也要保持兼容。
- 检查必须发生在核心注册之前，不能注册一半再“降级”。

### 4.4 降级边界

| 情况 | 应有行为 |
| --- | --- |
| 旧内容 + 范围内新前置 | 保留旧 ABI、行为和数据契约，正常加载 |
| 新内容 + 旧前置，仅缺表现或独立联动 | 禁用对应适配器；网络功能还要双方同意 |
| 缺核心注册、组件解码、必需菜单或协议 | 提前明确拒绝，指出内容包、当前版本和最低要求 |
| 前置超出声明范围 | 按声明拒绝；不能仅因版本较新就放行 |

**不能通过跳过已有方块、物品或组件注册来降级**，否则会把启动兼容问题变成存档损失。

## 5. 发行方式

### 5.1 单系列

- 继续用内嵌 Runtime 的单 jar，玩家只放一个文件。
- 内嵌的 Runtime 版本跟随该内容包的发布版本。

### 5.2 多系列 / 整合包

- 推荐用**一个共享的 `orient_framework` 前置 jar** + 不内嵌 Runtime 的内容包（`-slim`）。
- Fabric 的求解器在范围有交集时也能从多个内嵌候选里选一个；但共享前置的依赖集合更固定，整合包更好复现。
- NeoForge 只有范围交集且实际有候选时才可能成功，且不保证选最高版本。

### 5.3 所有系列都保持单 jar

- Fabric 不要求所有系列用同一份 Runtime 字节；只要依赖范围有交集，求解器可以选一个候选人。
- 但**同一个 Runtime 文件（同一份字节）仍是良好的发行纪律**，能减少不确定性；功能变化必须升 Runtime 版本，不能沿用旧版本号重新塞入不同实现。
- NeoForge 不能依赖“会选最新版”，多系列单 jar 组合必须逐个实测。

### 5.4 命名与 README

建议：

- `-bundled.jar`：内嵌 Runtime，适合单系列。
- `-slim.jar`：不内嵌 Runtime，需要单独装共享前置。

README 明确写：

1. 同一内容系列两种包**二选一**。
2. slim 需要独立 Runtime；bundled 的多系列组合以兼容表为准。
3. Fabric API 等其他必需依赖仍需安装；不要指导玩家手工拆 jar。

### 5.5 打包脚本的坑

- `build_candidates.py` 当前直接覆盖 Fabric 的 `jars` 列表和 NeoForge 的整份 JarJar metadata；以后若再嵌入其他依赖，会丢失原有声明。应保留其他依赖条目。
- Runtime 应独立构建、冻结版本和哈希，再供各内容包引用。

### 5.6 已发布的旧单 jar

- 已经发布、精确锁旧 Runtime 的单 jar，**不能靠新 Runtime 自动修好**；需要给旧内容补发一次放宽 `depends` 元数据的兼容版本（或 `-slim` 版本）。
- Fabric 的依赖覆盖文件可供整合包作者临时验证，但不能替代二进制兼容保证。
- 不要建议玩家手工拆开 jar 删除嵌套 Runtime。

## 6. 测试矩阵

| 场景 | 预期 |
| --- | --- |
| 旧内容 + 旧前置 | 通过 |
| 旧内容 + 新前置（范围内） | 通过 |
| 旧内容 + 新前置（范围外） | 明确拒绝，指出最低/当前版本 |
| 新内容 + 旧前置（缺必需 API） | 提前拒绝 |
| 新内容 + 旧前置（只缺可选特性） | 禁用适配器，降级运行 |
| 两个内容包内嵌不同 Runtime、范围有交集 | Fabric 求解器选一个；NeoForge 范围交集 + 实际候选，确认实际选中版本 |
| 两个内容包内嵌不同 Runtime、范围无交集 | 明确失败 |
| 两个内容包 + 共享前置 | 通过 |
| 外置版本低于/高于内嵌版本，交换包顺序 | 记录实际选中版本和来源 |
| 未重新编译的旧内容 jar + 新 Runtime | ABI 兼容通过 |
| 客户端 / 服务端能力不一致 | 协议协商后降级或明确拒绝 |

多系列断言应为：**Runtime 初始化一次，每个内容模块各初始化一次**；不能继续要求“模块总数为一”。

P3 的旧实验只证明了“互斥版本范围会失败”，不能代表当前统一 JarJar 坐标下的协商；旧 NeoForge 实验还用了不同坐标。上述组合需要重新实测。

## 7. 结论

- **单系列**：内嵌前置没问题。
- **多系列**：共享前置最稳，但不是唯一方案；Fabric 求解器在范围有交集时能从多个内嵌候选里选一个。
- 真正让旧内容接受新前置的，是 **API 兼容范围 + ABI 兼容 + 运行时能力查询/协商**，不是把版本锁死。
- 版本字符串优先用递增数字版本（`0.1.1`），不要依赖 `0.1.0-hotfixN`；Fabric 和 NeoForge 的排序不同。
- 不要依赖 NeoForge JarJar“肯定选最高版本”；它当前是 `findFirst()`。
- 已发布的精确锁旧包需要补发兼容元数据，不能靠新前置自动修复。
